# ASVS 5.0 mapping: file handling, untrusted execution, resource limits (Stage 8, Tier-2 environments)

Standard: OWASP ASVS 5.0.0, requirement text read from the official CSV (`v5.0.0` tag, `OWASP/ASVS`) on 2026-10-15. ASVS has no
chapter for running hostile code; these are the requirements that bear on it (V5 files, V13.2 outbound communication, V15 secure
coding and architecture, V16 error handling, V4.1.5 signatures). **The sandbox itself has had no external review (F73), runs on
gVisor on one development VM (F68), and the rows below say "Met" only for what a test shows.**

| ID | L | Requirement (shortened) | Status | Evidence or reason |
|---|---|---|---|---|
| v5.0.0-V5.2.1 | 1 | Only accept files of a size that can be processed without a loss of performance or denial of service | Partial | The node caps what it downloads (`downloadBytesMax`, 4 GiB) and unpacks (`DefaultLimits`: 200,000 entries, 4 GiB, depth 64; `extract_test.go` stops at each cap). 4 GiB is a generous ceiling, not a tuned one. The size cap on what authors upload to storage was not re-checked in this stage |
| v5.0.0-V5.2.3 | 2 | Compressed files checked against a maximum uncompressed size and file count before uncompressing | Partial | Archives are plain tar (no compression layer): entries and bytes are counted as they are written and stop at the cap, not before the first write |
| v5.0.0-V5.2.5 | 3 | No compressed files containing symlinks unless required, then an allowlist of targets | Partial | Container images need symlinks, so they are stored as links, never written through (`noLinkInParents`) and never followed by the node; targets are not allowlisted. Inside the sandbox they point only into a read-only or private tree. Snapshots handed to the verifier drop all links |
| v5.0.0-V5.3.2 | 1 | File paths for file operations come from internal data, not user-submitted names | Met | Run directories come from `os.MkdirTemp`; archive entry names are cleaned and must stay inside the target (`cleanName`, absolute, `..` and depth refused; tested) |
| v5.0.0-V5.3.3 | 3 | File decompression ignores user-provided path information (zip slip) | Met | `TestExtractRefusesEveryWayOutOfTheDirectory`: absolute names, `..`, a link then a file through it, hard links to nothing, outside or to a link; nothing was written outside |
| v5.0.0-V13.2.4 | 2 | An allowlist defines the external resources the application may communicate with | Partial | The guest has no network at all (every run, F69 for an allowlist); the escape suite's network probe is contained and its unconfined control escapes. The node downloads from the presigned URLs the control plane gives it and has no allowlist of its own |
| v5.0.0-V13.2.2 | 2 | Communication between backend components uses least-privilege accounts | Partial | The agent runs unprivileged; only a fixed set of helper commands is elevated. On the development VM the elevation is unrestricted passwordless sudo; narrowing it is a node-baseline task |
| v5.0.0-V15.1.3 | 2 | Documentation identifies time-consuming or resource-demanding functionality and how to prevent loss of availability | Met | ADR 0034 and 0035, runbook section 2 (sizing: cgroup peak plus workspace limit) and the limits in the spec (`time_limit_s`, memory, disk, pids, output) |
| v5.0.0-V15.2.2 | 2 | Defences against loss of availability from resource-demanding functionality | Partial | Per-run wall, memory, pids, disk, output and trace caps are enforced and tested (TLE, MLE, OLE, process limit, disk-fill, drill). There is no admission control by memory across concurrent runs (F74) and no per-organization quota on environment runs was built |
| v5.0.0-V15.2.5 | 3 | Additional protections around dangerous functionality and risky components | Partial | Hostile code runs only in gVisor on a judge node, never on API or web hosts; eligibility is enforced in Postgres. It is not a microVM and has had no external review (F68, F73) |
| v5.0.0-V15.4.2 | 3 | Check and use of a resource's state done atomically (TOCTOU) | Partial | The unpacker checks parents with `Lstat` and then writes; it is the only writer in a directory only it creates, so nothing can swap a link between the two, but this is reasoning, not a test. The copy-in and copy-out run while the sandbox is not running |
| v5.0.0-V16.5.3 | 2 | Fails gracefully and securely, no fail-open when an exception occurs | Met | A sandbox failure is verdict `SE` and the run fails and retries; `eligible` is computed in the database and defaults to refusing; a trace that does not hold together is refused, not repaired (`trace.ts`); the e2e failures found in this stage were all loud |
| v5.0.0-V4.1.5 | 3 | Per-message digital signatures on highly sensitive requests that traverse several systems | Partial | The node signs each trace (Ed25519, domain `AURA-TRACE-V1`) and the control plane verifies the signature over the exact bytes before parsing (`env-routes.ts`, `trace.ts`). The rest of the node protocol relies on mTLS and lease epochs as in Tier-1 |
| v5.0.0-V1.4.3 | 2 | Dynamically allocated memory and resources are released | Partial | The drill shows no process, mount, cgroup or directory left after hostile runs. A stale sandbox from an earlier killed test run was found alive 90 minutes later and nothing sweeps such leftovers at startup (F71) |

Not applicable here: V5.3.1 (nothing is served from a public folder), V1.2.8 and chapters on browsers and OAuth.
